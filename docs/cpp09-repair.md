# CPP09 評価指摘への修正と検証

日付：2026-10-01。対象：`cpp09/ex00`〜`ex02`。手元の subject Version 3.3 と、今回受け取った評価指摘に基づく。

## 原因と修正

| 対象 | 原因 | 修正後 |
|---|---|---|
| ex00 | double への変換で `1000.0000000000000000000001` が 1000 に丸められ、上限超過を見逃す | 変換前の十進文字列で符号と 1000 との大小を判定。先頭ゼロ・小数点・指数表記も扱う |
| ex01 | int のスタックと整数除算が途中の小数を切り捨てる | `std::stack<double>` のみを宣言し、演算・戻り値・表示まで double を保持。list の指定と整数へのキャストを削除 |
| 回帰テスト・解説 | `5 2 / 2 *` の結果を 4 として検査し、整数除算を正しい設計として説明していた | 期待値を 5 に修正。評価指摘の 6912 と、Fraction による独立した正解との照合を追加 |
| ex00・ex01 | 非ゼロ値の乗除算が表現範囲を下回ると、0 を正常結果として出す | ゼロへのアンダーフローを明示的なエラーにする。実際の 0 は正常に扱う |

ex00 は追加済みの検証関数が呼ばれておらず、作業開始時の `-Werror` ビルドが unused-function で失敗した。関数を入力処理へ統合した。DB の空・不正・重複日付・読込失敗も検出し、再読込は完全な検証の成功後に入れ替えるため、失敗時に既存 DB が部分更新されない。

追加した指数処理は最終確認で `1e4`・`.1e5`・`.01e6` の誤受理を発見し、飽和上限を文字列長 + 4 に修正した。短い仮数と指数 403 通りを回帰テストに加え、別の監査で 17,745 ケースの字句判定を確認した。

ex02 の Ford–Johnson 実装は、独立監査で不具合を確認しなかったため維持した。ペア対応は値ではなくインデックスで保持し、勝者を再帰的に整列し、敗者と奇数の余りを同じ Jacobsthal 順で挿入する。敗者の二分探索は相手の勝者より前に限定する。

## 評価指摘の再現結果

```text
2011-01-03 | 1000.0000000000000000000001
→ Error: too large a number.

2011-01-03 | 1000.0000000000000000000000
→ 2011-01-03 => 1000 = 300

./RPN "8 3 / 2 * 6 * 6 * 6 * 6 *"
→ 6912

./RPN "5 2 / 2 *"
→ 5

./RPN "0 3 - 2 /"
→ -1.5
```

## 検証方法と結果

再実行はリポジトリのルートで行う。提出コードの一時コピーをビルドし、元のファイルやビルド生成物を変更しない。

```sh
python3 scripts/verify_cpp09.py
python3 scripts/verify_cpp09.py --sanitize --quick
python3 scripts/verify_cpp09.py --valgrind  # Linux、Valgrind 導入済みの場合
```

Linux の最終変更後の再実行は、変更のあった ex00 に限定した。ex01・ex02 は同じソースで成功している結果を採用した。ホストのリポジトリを read-only でマウントし、コンテナ内のコピーを検証した。検証用コンテナは終了後に削除済み。

比較回数の監査は一時コピーの private ヘルパーを公開し、値の比較箇所のみを数える。提出実装にはテスト専用 API・比較カウンター・std::sort を追加しない。CLI でも別途 Python `sorted` と照合する。詳細と公開参考資料は [テスト説明](../tests/cpp09/README.md) にまとめた。

## 検証の境界

- 修正済みコードの自動検証と独立レビューの結果であり、正式な再評価の合格を示すものではない。
- 範囲判定は十進文字列に対して厳密。換算と RPN の計算自体は double の精度で行う。非有限値とゼロへの全桁消失は拒否する。
- 10 要素以上の全順列や、実ディスクの途中読込エラー注入は実行していない。大量入力は固定・生成ケースで確認した。
- CPP05〜CPP09 の共通スクリプトは push 前に再実行した。CPP00〜CPP04 の再検証と、他モジュールの新たな仕様監査は行っていない。
